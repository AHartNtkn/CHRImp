## Cycle

1. **Measure the integrated system.** Use the maintained tools in `docs/performance.md`: validated workloads and regressions, CPU flame graphs, and allocation/lifetime diagnostics when relevant. Reuse evidence that still answers the question. Profile a material slow, memory-heavy, stalled or censored case, and retain an unchanged control. Rotate coverage beyond synthesis: joins, graph/rewrite workloads, identity changes, independent/correlated choices, propagation, preparation, observation and release as indicated by risk. A concrete uncovered risk can justify another workload; an exhaustive workload catalogue is unnecessary.
2. **Explain the resource cost.** Identify work that could disappear or scale differently. Keep CPU, wall time, allocation, retained state, search progress and output costs distinct. Inclusive profile frames overlap. Censoring is not a completed runtime, and more internal work is not necessarily useful progress. Instrument only an actual unresolved diagnostic question.
3. **Brainstorm independently.** Use the brainstorm-solution skill with distinct agent priorities and fresh inspiration words. Give agents the measured problem, semantics and relevant code; do not seed a preferred technique. Research primary literature when it resolves a relevant question. Consider different representations, execution foundations, algorithms and compiler transformations. The current engine and its counters impose no architectural constraint. Apply the ponytail discipline to avoid machinery whose cost or purpose is unjustified.
4. **Select bounded spikes.** Choose the few hypotheses with the highest decision value, not one implementation per suggestion. State the mechanism, applicability, likely adverse case, expected meaningful gain, comparable outputs, resource budget and falsifier before coding. Use isolated worktrees from a common current baseline. Allow independent implementations in parallel; serialize measurements. Include setup, demanded work, delivery, retained resources and release. Test consequential combinations when individual wins plausibly interact.
5. **Choose and integrate.** Advance substantial end-to-end or scaling improvements that preserve correctness and sharing. Compare winners against the current baseline and each other where their effects overlap. Retain explicit speed/memory tradeoffs; no universal winner is required. Fix actual correctness defects and validate affected production paths, including optional inspection/history when touched. Review the changed responsibilities, integrate safe winners into the landing branch, run relevant checks and commit. Migrate consumers to the selected implementation; experimental controls do not become permanent product architecture.
6. **Repeat from the integrated result.** Report the actual gain, loss, rejected hypothesis or remaining uncertainty that changed the decision. If no credible major improvement is supported, record that result and await new evidence or the next wake. Do not polish a weak spike through microoptimization or rerun the same inconclusive experiment without a changed premise.

## Bounds and stopping within a cycle

Use an initial planning budget of roughly one hour of active investigation/implementation per cycle and at most two minutes of serialized measurement. Select appropriate per-workload source, cleanup, external time and memory limits before execution. A more demanding comparison may receive a larger explicit budget when its expected decision value justifies it. A cycle can span wake-ups; the same experiment does not receive a fresh budget simply because another wake occurs. Expiration yields an honest bounded result and reassessment, never automatic extension.

Real progress changes an architectural or integration decision: a supported major gain, a useful rejection, an applicability boundary, a consequential combination, or a diagnosed regression. Additional counters, documents, repeated benchmarks, marginal improvements and possible ideas are not independently unfinished delivery. Continue the ongoing service without treating every remaining possibility as a required implementation.
